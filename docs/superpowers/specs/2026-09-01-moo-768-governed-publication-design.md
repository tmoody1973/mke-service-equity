# MOO-768 Governed Food Equity Publication Contract

**Status:** Approved by Tarik on 2026-09-01

**Issue:** MOO-768 — Plan 6A — Governed Food Equity publication lifecycle

**Prepared:** 2026-09-01

**Implementation gate:** Satisfied by Tarik's explicit “Approve MOO-768 publication contract.”

## Decision summary

MOO-768 adds a forward-only, auditable release mechanism around the already validated Equity
Baseline and Food Equity runs. A public release is one exact Food run, that run's exact pinned
Equity Baseline, the immutable analytical rows behind both runs, and an explicit manifest of
source snapshots and food-resource versions.

The database owns publication state and atomicity. A dedicated server-side command is the only
ordinary way to request a publication change. The public web application is read-only and selects
the single current release; it never chooses a latest run and never falls back to validated data.

This task proves the mechanism on a confirmed expiring Neon development branch. It does not
publish the authoritative Plan 2 or Plan 3 development runs and does not authorize a production
release.

## 1. Existing facts this contract preserves

- Equity Baseline run status already names draft, validated, published, superseded, and failed,
  but the Plan 2 trigger rejects publication transitions.
- Food run status currently permits only draft, validated, and failed, and its Plan 3 trigger
  requires an exact validated Equity Baseline ID and output hash.
- The authoritative development runs remain validated and unpublished:
  - Equity Baseline: 502e2a04-b013-53cd-8b09-c9144862701a.
  - Food Equity: 97bd1cdf-bf96-573f-8fcf-92e8676925d4.
- Public Atlas, Compare, and Opportunity currently fail closed with no_published_run.
- Local preview may select only one explicit validated Food run under development-only,
  server-only configuration and remains visibly unpublished.
- A deployment, browser request, pipeline run, or ordinary data query cannot publish.
- Missing data, output hashes, run fingerprints, score values, methodology, provenance, and
  quality states are not changed by publication.

## 2. Publication unit and current-release rule

### 2.1 One exact release bundle

A release record identifies:

- one Food score run ID and output hash;
- that Food run's stored Equity Baseline run ID and output hash;
- one canonical bundle fingerprint;
- the exact Equity and Food tract-score rows;
- the exact Equity and Food score-component rows and their input value rows;
- every contributing source snapshot needed for lineage and reproduction;
- every exact food-resource version used by the approved scoring inventory;
- an explicit public redistribution decision for every pinned source/resource set;
- publication, approval, actor/process, command, and validation metadata.

Run IDs alone are not treated as a complete release manifest. Publication membership is persisted
relationally so a public query never reconstructs the release from a category, maximum timestamp,
newest snapshot, or mutable source pointer.

### 2.2 Current means one database fact

Current is not inferred from a date. It is the zero-or-one release row whose state is published.
A partial unique index enforces at most one such row. Once the first release exists, an ordinary
replacement transaction ends with exactly one current release. An emergency withdrawal may
intentionally leave zero; the public selector then fails closed.

The selector must reject duplicate, incomplete, hash-mismatched, or internally inconsistent
current rows rather than choosing one.

### 2.3 Release identity

The canonical bundle fingerprint hashes a versioned manifest containing sorted immutable IDs,
stored fingerprints/hashes, membership roles, redistribution decisions, and required audit
metadata. It excludes timestamps generated by the publication transaction so an exact retry has
the same identity.

The Food run ID is unique across release records. A previously published or superseded Food run
cannot be published again under a new release ID.

## 3. State machines

### 3.1 Equity Baseline runs

Allowed transitions are:

    draft -> validated
    draft -> failed
    validated -> published
    published -> superseded

The same published Equity Baseline may remain published when a replacement Food run pins the
same baseline. It becomes superseded only when no current Food release pins it.

Rejected transitions include direct insert as validated/published/superseded, draft or failed to
published, validated to failed, published to validated, superseded to published, every transition
out of failed, and every transition out of superseded.

### 3.2 Food Equity runs

Allowed transitions are:

    draft -> validated
    draft -> failed
    validated -> published
    published -> superseded

All other transitions are rejected. In particular, draft/failed publication, re-publication,
published-to-validated, and superseded-to-current are prohibited.

### 3.3 Release records

Allowed transitions are:

    create as published
    published -> superseded

A release cannot be inserted as superseded, returned to published, updated to point at another
run, or deleted. Replacement creates a new published release and supersedes the old one in the
same transaction. Emergency withdrawal only supersedes the current release after a separate
approval and leaves public mode unavailable.

## 4. Eligibility and integrity

Immediately before any state change, the publication transaction locks and revalidates the
candidate. It must prove:

1. Food is validated, has completion time, validation evidence, output hash, and immutable run
   fingerprint.
2. Its pinned Equity Baseline exists, is validated or is the exact currently published baseline,
   has validation evidence and output hash, and matches both stored Food pin fields.
3. Canonical geography, scores, components, indicator/access values, source lineage, counts,
   exclusions, quality states, and output hashes reconcile to the reviewed release manifest.
4. Every member belongs to the exact Food/Baseline lineage. There are no missing, duplicate,
   orphaned, wrong-run, or ambiguous rows.
5. Every source/resource membership has an explicit reviewed decision. No public membership is
   inferred from type, status, date, distance, or latest record.
6. The expected current release ID supplied by the operator still matches the database.
7. The request's dry-run hash, approval ID, idempotency key, and exact confirmation value match.

Any failed condition aborts the entire transaction.

## 5. Relational release manifest

The forward migration adds a small governed publication schema:

- **atlas_publications** — release identity, exact run/hash pins, state, timestamps, approval,
  actor/process, dry-run hash, bundle fingerprint, replacement lineage, and validation summary.
- **atlas_publication_score_members** — one row per canonical geography, pinning the exact Food
  and Equity score IDs.
- **atlas_publication_equity_component_members** — exact Equity component and indicator-value IDs.
- **atlas_publication_food_component_members** — exact Food component and access-metric-value IDs.
- **atlas_publication_source_snapshot_members** — exact snapshot IDs, lineage role,
  redistribution decision, terms reference, and attribution requirement.
- **atlas_publication_resource_version_members** — exact resource-version IDs, scoring/display
  role, redistribution decision, and required warning/attribution when applicable.
- **atlas_publication_audit_events** — append-only attempted/succeeded/rejected/failed/dry-run
  evidence linked by idempotency key and release/request identity.

Foreign keys use restrict for publication history. Existing analytical cascade paths may remain
for unpublished drafts, but database guards prevent update or deletion of any row pinned by a
published or superseded release.

Membership tables are populated from a canonical release manifest and independently reconciled
to database lineage. A publication cannot become current with an incomplete manifest.

## 6. Public resource and redistribution policy

### 6.1 Decisions

Every pinned source and food-resource set receives one of these decisions:

- public_derived_results — derived tract evidence may be shown with required attribution/terms;
- public_direct_display — exact resource records may be shown with required warnings and credit;
- internal_reproduction_only — retained to reproduce the score but not returned publicly;
- prohibited_public_use — cannot enter a public response.

No blank or implicit decision is allowed.

### 6.2 First-release policy

- Census, CDC, and USDA-derived tract evidence may be public with source, vintage, definition,
  retrieval information, and attribution.
- OSM/Geofabrik-derived access results may be public only with OpenStreetMap-contributor and
  Geofabrik attribution and the recorded ODbL obligations.
- MCTS-derived scheduled-service evidence may be public only with the feed's last-updated and
  valid-through dates plus the required not-sponsored/not-operated statement.
- The Plan 3 EmergencyFood_MKE_2024 source and every resource version derived from it are
  prohibited_public_use because the data are stale, unverified, and have no approved reuse terms.
- The separately approved Pantries 2026 Atlas artifact remains governed by the MOO-754
  release-pinned display-only contract. MOO-768 does not treat it as a scoring source, infer it
  from database resources, or broaden its approval. If it is later moved into this relational
  bundle, that requires its own reviewed resource manifest and public_direct_display decision
  preserving the exact checksum, credit, terms link, and Check before visiting warning.
- FNS retailer versions needed to reproduce grocery routing are pinned exactly. Direct public
  display is disabled in the first release unless a separate reviewed display decision approves
  the exact fields and attribution.

Public responses exclude internal and prohibited members. The selector fails closed if a public
display membership lacks a terms reference, attribution rule, approved quality state, or required
warning.

## 7. Atomic publication and concurrency

Publication uses one database transaction and a transaction-scoped advisory lock for the single
Atlas release channel.

Within that transaction the controlled database operation:

1. checks the expected-current compare-and-swap value;
2. locks the candidate runs and current release;
3. revalidates hashes, evidence, lineage, manifest membership, and redistribution decisions;
4. writes the immutable release and member rows;
5. supersedes the old Food run and old release when present;
6. supersedes the old baseline only when the new release does not reuse it;
7. promotes the candidate baseline when needed and promotes the candidate Food run;
8. writes the successful audit event; and
9. verifies exactly one internally consistent current release before commit.

The partial unique index is a final concurrency backstop. Any error rolls back all release,
membership, and status changes. No partial current bundle can survive.

## 8. Permissions and execution boundary

Four capabilities remain separate:

- migration owner — owns schema/functions; used only for reviewed migrations;
- pipeline writer — may create and validate development analytical runs but cannot publish;
- publication operator — may execute the controlled publication operation but has no general
  analytical table update/delete permission;
- application reader — may read the server-only current-release boundary and required immutable
  rows but cannot execute publication or mutate data.

Production must use distinct credentials for the application reader and publication operator.
Development verification may use the confirmed branch owner only to prove the permission model
and controlled operation; that exception does not become the production deployment design.

The publication operation is not exported from the web package, route handlers, Server Actions,
or the public database package surface used by application requests. Browser code cannot import
it. Vercel build/start and ordinary Atlas queries have no write path.

## 9. Operational command

A separate server-only TypeScript CLI provides:

    publication dry-run
    publication publish
    publication reconcile
    publication withdraw

Dry-run is mandatory before publish or withdraw. It is read-only and produces a canonical,
secret-free report under an ignored local report directory. Publish requires:

- direct server-only database configuration;
- explicit environment name;
- candidate Food run ID;
- expected current release ID or the literal none;
- approval ID;
- idempotency key;
- exact dry-run report hash;
- exact candidate run ID confirmation;
- actor identifier and reason;
- production guard confirmation when the target is production.

Withdraw requires the same controls, the exact current release ID confirmation, and a separate
incident/release approval. Reconcile is read-only.

The CLI checks the target database identity before any write and refuses production unless the
separate Gate 3 approval inputs are present. Arguments and reports never contain credentials.
A safe retry with the same idempotency key and identical request returns the recorded result;
reusing a key with different inputs fails.

## 10. Audit evidence

Every reachable command attempt records or emits:

- action and outcome;
- idempotency key;
- environment and sanitized database identity;
- actor/process identifier;
- approval ID and reason;
- command/schema version and git commit;
- candidate and prior release/run IDs;
- exact run output hashes and bundle/dry-run hashes;
- validation and membership counts;
- timestamps;
- redacted failure code when applicable.

Audit rows are append-only. Credentials, URLs containing credentials, API keys, raw environment
values, and unbounded validation payloads are prohibited. A failure before database reachability
still writes the secret-free local report.

## 11. Rollback, supersession, and recovery

Rollback is forward-only:

- A bad candidate that fails before commit leaves the current release unchanged.
- A replacement publishes a different fully validated candidate and atomically supersedes the
  current release.
- A previously superseded Food run is never made current again. Returning to equivalent earlier
  analytical inputs requires a newly validated, independently identified candidate allowed by
  the deterministic run contract; history is not rewritten.
- An approved emergency withdrawal supersedes the current release and leaves zero current
  releases, causing every public workflow to fail closed until a new candidate is approved.
- Published and superseded rows are never deleted or edited to simulate rollback.
- Selector corruption or a post-publication integrity mismatch causes fail-closed public reads,
  incident evidence, and a reviewed forward repair or replacement. Operators never hand-edit a
  status, member row, hash, or pointer.

## 12. Public selector

The server-only selector queries the singular published release, exact Food run, exact pinned
baseline, hashes, publication identity, and manifest summary using parameterized SQL. It validates
the strict contract and returns:

- mode published;
- immutable publication ID and published timestamp;
- Food and Equity run/methodology IDs and output hashes;
- source/resource publication identity needed by downstream repositories and cache keys.

No row returns no_published_run. Duplicate or inconsistent rows return data_incomplete. The
selector never falls back to validated, draft, failed, or superseded data and never orders by a
latest timestamp. Published caches key on immutable publication ID plus normalized request
identity. Preview remains dynamic, private, and unchanged.

## 13. Verification and approval gates

Implementation must prove on a confirmed expiring Neon development branch:

- reviewed forward migration scope, enums, constraints, indexes, foreign keys, triggers,
  permissions, PostGIS, and zero mutation of existing validated runs;
- controlled fixture publication, replacement, safe retry, withdrawal, and failure rollback;
- rejection of every invalid transition and mutation/deletion of released content;
- exact manifest reconciliation for scores, components, value rows, snapshots, resources, hashes,
  terms, and quality states;
- public exclusion of prohibited emergency-food and unapproved resource records;
- server-only selector behavior and absence of a web publication path;
- database unit/integration, Python, TypeScript, migration, security, build, and final live replay
  evidence.

Development fixture publication proves the mechanism only. Publishing the authoritative
development runs or any production run requires a later, explicit Gate 3 decision naming the
exact dry-run evidence and candidate.

## 14. Out of scope

- Actual production publication or public release.
- Publishing the authoritative Plan 2 or Plan 3 development runs during implementation.
- Recalculating or changing any score, formula, weight, band, Priority, source value, or quality
  state.
- Acquiring new source data or assuming a missing license/verification.
- Making emergency food, investment, land, or other context change a score.
- Browser publication controls, authentication UI, AI decisions, destructive rollback, or
  production data mutation from local development.
